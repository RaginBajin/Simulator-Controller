## Project Context Analysis

### Requirements Overview

**Functional Requirements:**
- Telemetry capture & data management (FR1–FR10, FR1a/FR1b): auto-detect iRacing, capture at configurable rates, lap detection, gap handling, corner segmentation, derived metrics, import/export, local storage in open formats.
- AI coaching & analysis (FR11–FR19): fast post-session debrief, per-corner analysis, telemetry-grounded insights, conversational follow-up, session and lap comparison, training recommendations.
- AI provider management (FR20–FR24): BYOK credentials, validation, provider status, graceful operation without AI.
- Visualization & debrief (FR25–FR30): lap-distance charts, multi-lap overlay, per-lap and session summaries, debrief as serializable data.
- Session history & progress (FR31–FR33): local history browsing, filtering, cross-session progress metrics.
- Desktop integration (FR34–FR41): system tray background app, notifications, tray-accessed debrief, auto-start, updates, storage location, session-type detection, audio preferences.

**Non-Functional Requirements:**
- Performance: NFR1–NFR6a (CPU/RAM limits, per-lap processing budget, chart render latency, progressive AI streaming, fast tray readiness).
- Reliability: NFR7–NFR11 (capture completeness, gap detection, crash safety, graceful AI failure, iRacing shutdown recovery).
- Data integrity: NFR12–NFR16 (timestamp accuracy, lap boundary correctness, deterministic metrics and exports, checksums).
- Security: NFR17–NFR20 (OS credential storage, no key leakage, allowlist-based sharing, signed updates).
- Integration: NFR21–NFR24 (IRSDK version resilience, AI timeout/retry, fast iRacing detection, IBT backward compatibility).
- Usability: NFR25–NFR28 (fast onboarding, zero-touch recording, VR-friendly flow, coaching readability and correctness).

**Scale & Complexity:**
- Primary domain: Windows-first desktop app with native system tray + rich UI + AI analysis.
- Complexity level: High.
- Estimated architectural components: ~12–15 (capture, preprocessing, storage, AI providers, streaming, IPC, charting, debrief model, history/progress, settings, notifications, update system).

### Technical Constraints & Dependencies

- Windows-only dependency for iRacing telemetry (IRSDK shared memory and IBT files).
- Offline-first operation for capture, preprocessing, and debrief viewing.
- BYOK AI provider model with OS-level credential storage.
- System tray as the primary runtime surface; notifications must be minimal and high-signal.
- Telemetry capture at 30–60Hz with strict CPU/RAM budgets.
- Local storage in open formats (Parquet + SQLite) and deterministic exports.
- Tauri 2.0 desktop shell with Rust core + web UI.

### Cross-Cutting Concerns Identified

- Data pipeline integrity across capture → preprocess → storage → AI → UI.
- IPC boundaries between Rust core and UI for large telemetry slices and streaming AI.
- Graceful degradation when AI providers are unavailable.
- Robust gap/partial-lap handling without losing diagnostic data.
- Security and privacy of credentials and shared outputs.
- Observability and performance instrumentation across the pipeline.
- Accessibility (keyboard navigation + contrast) and desktop-resize responsiveness.

## Core Architectural Decisions

### Data Architecture

**Storage Split:**
- Parquet for telemetry time‑series.
- SQLite for metadata and summaries.

**Parquet Library:**
- `parquet` crate (Apache Arrow Rust).

**SQLite Access Layer:**
- `sqlx` with SQLite enabled.

**SQLite Bundling:**
- Bundled SQLite to ensure consistent behavior across machines.

**Migrations:**
- SQLx migrations.

**Data Modeling:**
- Schema‑first: SQL migrations define schema; Rust structs map to SQL; Arrow schema defines Parquet layout.

**Validation Strategy:**
- Hybrid: minimal validation at capture (required fields, timestamp monotonicity); full validation during preprocessing/analysis.
- Invalid samples retained with flags; gap markers emitted; derived metrics skip invalid points; debrief shows warnings.

**Caching:**
- Rust‑side in‑memory LRU for active session slices (cap TBD).

**Failure Modes & Preventive Controls (Data Layer):**
- Parquet partial write/corruption on crash → write to temp + atomic rename + checksum on read (aligns with NFR9/NFR15).
- Schema drift between SQLite and Parquet → central schema definitions + migration gating + CI schema compatibility tests.
- SQLx migration failure at startup → fail fast before capture starts + rollback/backup strategy + clear error surfacing.
- Hybrid validation flags too aggressive → tiered validation rules + telemetry gap markers instead of hard rejects.
- Timestamp monotonicity issues → enforce at capture, log and flag any violation; maintain gap markers for discontinuities.
- LRU cache memory blow‑up → add cap (TBD) + metrics; ensure eviction is observable in logs.

### Authentication & Security

**Authentication Model:**
- Local‑only for MVP (no sign‑in).
- Defer account system to Growth phase.

**API Key Storage (BYOK):**
- `keyring` crate with Windows‑only credential store (`windows-native`).

**IPC Security:**
- Baseline: strict permissions for sensitive commands now; expand as features stabilize.

**Encryption at Rest:**
- None (rely on OS disk encryption).

**Sharing/Export Privacy:**
- Allowlist‑only export fields (default private).

**Updates:**
- Tauri updater with mandatory signing.

**Critical Risks & Mitigations:**
- No account system now → features that need identity (sharing, sync) must be clearly gated as Growth; avoid partial backend scope creep.
- Baseline IPC permissions → ensure sensitive commands are scoped and parameter‑validated from day one (no wildcard command permissions).
- No encryption at rest → warn users if OS disk encryption is disabled; never store secrets outside keyring.
- Windows‑only keyring → document the path for future cross‑platform support (feature flags + conditional compilation).
- Allowlist export → define and test the allowlist in CI to prevent accidental data leakage.

**ADR‑SEC‑1: Local‑Only Authentication (MVP)**
- **Context:** MVP focuses on local capture + debrief. Accounts introduce backend scope and compliance.
- **Decision:** No sign‑in for MVP; defer accounts to Growth.
- **Consequence:** Sharing/sync features are gated; local privacy and speed improved.

**ADR‑SEC‑2: OS Credential Store for BYOK Keys**
- **Context:** PRD requires OS‑level credential storage; keys must never be in files/logs.
- **Decision:** Use `keyring` with Windows‑native backend.
- **Consequence:** Strong local security; cross‑platform support deferred.

**ADR‑SEC‑3: Capability‑Based IPC Security**
- **Context:** Tauri commands can expose sensitive actions.
- **Decision:** Baseline permissions: strict for sensitive commands, expand later.
- **Consequence:** Prevents over‑permissioned IPC while allowing iteration.

**ADR‑SEC‑4: No Encryption at Rest (MVP)**
- **Context:** Data must remain open‑format; encryption adds complexity and key management.
- **Decision:** Rely on OS disk encryption; no app‑level encryption for MVP.
- **Consequence:** Simpler pipeline, but users rely on OS protection.

**ADR‑SEC‑5: Allowlist‑Only Sharing**
- **Context:** Shared exports must not leak private data.
- **Decision:** Share only explicitly allowlisted fields.
- **Consequence:** Strong privacy control; requires allowlist governance.

### API & Communication Patterns

**IPC Strategy:**
- Commands for request/response (data fetches, user actions).
- Events for state changes, streaming, and progress signals.

**Payload Strategy:**
- Hybrid: windowed JSON slices for UI rendering; file‑based transfer for exports/heavy loads.

**Error Contract:**
- Structured error object: `{ code, message, details?, retryable? }`.

**Event Naming Convention:**
- Namespaced `domain:action` in kebab‑case (e.g., `session:state-changed`, `ai:token-received`).

**IPC Constraints (Tauri):**
- Command arguments and return values must be JSON‑serializable.
- Events are one‑way, fire‑and‑forget messages for lifecycle/state updates.

**Failure Modes & Preventive Controls (IPC Layer):**
- Oversized JSON payloads → enforce windowing + downsampling + size limits; prefer file‑based transfer for heavy exports.
- Event storms during capture/AI streaming → throttle events, batch tokens, and define backpressure rules.
- Command/event schema drift → central typed contracts in Rust + TS; CI contract checks.
- Error ambiguity across boundary → enforce `{ code, message, details?, retryable? }` and map codes to UX messages.
- Event ordering issues → include `sequence_id` for streams; frontend drops out‑of‑order tokens.
- Missing events on resume → state snapshot command on app open; events are used for deltas only.

## Implementation Patterns & Consistency Rules

### Pattern Categories Defined

**Critical Conflict Points Identified:**
8 areas where AI agents could make different choices (naming, structure, formats, events, errors, loading, tests, logging).

### Naming Patterns

**Database Naming Conventions:**
- Tables: `snake_case` plural (e.g., `sessions`, `lap_summaries`).
- Columns: `snake_case` (e.g., `session_id`, `started_at`).
- Foreign keys: `{table}_id` (e.g., `session_id`).
- Indexes: `idx_{table}_{column}` (e.g., `idx_sessions_started_at`).

**API/IPC Naming Conventions:**
- Tauri command names: `snake_case` (e.g., `get_session_data`).
- Frontend invoke wrappers: `camelCase` (e.g., `getSessionData()`).
- Event names: `domain:action` in kebab‑case (e.g., `session:state-changed`).

**Code Naming Conventions:**
- Rust: functions `snake_case`, types `PascalCase`, constants `SCREAMING_SNAKE_CASE`.
- TypeScript: functions/vars `camelCase`, types/interfaces `PascalCase`.
- React components: `PascalCase`.
- Frontend file names: `kebab-case` (e.g., `session-card.tsx` exporting `SessionCard`).

### Structure Patterns

**Project Organization:**
- Frontend: feature‑based under `src/features/<feature>/`.
- Shared code: `src/lib/` for utilities/types, `src/state/` for Zustand stores, `src/hooks/` for shared hooks.
- Rust: workspace with `crates/*`; `src-tauri/` as app shell.

**Testing Locations:**
- Frontend unit tests co‑located as `*.test.ts(x)` next to the module.
- Rust unit tests in module `mod tests`; integration tests under `crates/*/tests` and `src-tauri/tests`.

### Format Patterns

**API Response Formats:**
- Success: direct typed payload (no global `{data: ...}` wrapper).
- Errors: `{ code, message, details?, retryable? }`.

**Data Exchange Formats:**
- JSON fields: `camelCase` for IPC payloads.
- Dates/times: ISO 8601 UTC strings (`YYYY-MM-DDTHH:mm:ssZ`).
- Booleans: `true`/`false`.
- Nullable values: explicit `null` (avoid missing keys for optional fields).

### Communication Patterns

**Event System Patterns:**
- Event name format: `domain:action`.
- Event payload includes: `type`, `timestamp`, `version`.
- Streaming payloads include `sequenceId` for ordering.

**State Management Patterns:**
- Async state: TanStack Query only.
- UI/global state: Zustand stores under `src/state`.
- No direct state mutation outside Zustand actions.

### Process Patterns

**Error Handling Patterns:**
- Rust: single `AppError` enum → serialized to structured JSON error.
- Frontend: centralized error mapper (code → user message).
- User‑facing errors are concise; debug detail stays in logs.

**Loading State Patterns:**
- Use local loading states in components.
- Use global “busy” only for app‑wide blocking actions (e.g., migrations).

### Enforcement Guidelines

**All AI Agents MUST:**
- Use the established naming conventions (DB/IPC/TS/Rust).
- Use IPC error format `{ code, message, details?, retryable? }`.
- Use event names `domain:action` with `type/timestamp/version`.
- Keep telemetry payloads windowed; do not send full sessions over IPC.
- Add/adjust types in both Rust and TypeScript when IPC payloads change.

**Pattern Enforcement:**
- PR review checklist confirms naming/format/event conventions.
- CI lint checks enforce file naming and test placement.
- Contract updates require updating `src/lib/types.ts` and Rust DTOs.

### Pattern Examples

**Good Examples:**
- Command: `get_session_data` (Rust) → `getSessionData()` (TS wrapper).
- Event: `ai:token-received` with `{ type, timestamp, version, sequenceId, token }`.
- DB table: `session_summaries` with `session_id`.

**Anti‑Patterns:**
- Mixed JSON casing in IPC payloads.
- Emitting events without `sequenceId` for streams.
- Sending full telemetry arrays without windowing/downsampling.

### Architectural Boundaries

**API Boundaries:**
- Tauri command surface is the only Rust ↔ frontend API boundary.
- Commands: request/response (data fetches, user actions).
- Events: state changes + streaming (AI tokens, progress updates).

**Component Boundaries:**
- Frontend features are isolated by folder (`src/features/*`).
- Shared UI primitives live under `src/components/ui/`.

**Service Boundaries:**
- Rust crates enforce boundaries:
  - `storage` is a leaf crate.
  - `telemetry-engine` and `ai-provider` depend on `storage`.
  - `src-tauri` orchestrates all crates.

**Data Boundaries:**
- SQLite: session metadata, summaries, AI results.
- Parquet: raw telemetry time‑series.
- No raw Parquet is sent to the frontend; only windowed slices.

### Integration Points

**Internal Communication:**
- Tauri commands + events (IPC) with structured error objects.
- Zustand stores consumed by UI features; TanStack Query for data.

**External Integrations:**
- iRacing IRSDK: `crates/telemetry-engine/irsdk/*`
- AI Providers: `crates/ai-provider/adapters/*`
- OS Credential Store: `crates/ai-provider/credential.rs` (keyring)
- Updates: Tauri updater plugin
- Notifications: Tauri tray + OS notifications

**Data Flow:**
- IRSDK → telemetry-engine → storage (Parquet + SQLite) → AI provider → Tauri events → UI.

### File Organization Patterns

**Configuration Files:**
- Root config for JS/TS tooling; Rust config under `src-tauri/` and `crates/*`.

**Source Organization:**
- Frontend: feature‑based + shared libraries in `src/lib`.
- Rust: crate‑based.

**Test Organization:**
- Frontend tests co‑located.
- Rust integration tests under `crates/*/tests` and `src-tauri/tests`.

**Asset Organization:**
- Frontend assets under `src/assets`.
- App icons under `src-tauri/icons`.

### Development Workflow Integration

**Development Server Structure:**
- `cargo tauri dev` runs Vite + Rust core.

**Build Process Structure:**
- Vite builds frontend; Tauri bundles output into MSI/NSIS.

**Deployment Structure:**
- GitHub Actions builds artifacts; releases feed updater.
